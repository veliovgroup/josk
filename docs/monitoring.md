# Monitoring claims and recovery

`setInterval` keeps a claimed task in storage until its handler calls `ready()` or the zombie deadline arrives. A due task without a claim may simply be backlog. A claim with `executeAt` near or past its deadline is **not proof of a stuck handler**: the handler may still be running, and old records can retain a stale lease from releases that did not clear it on `update()`.

Use a threshold such as `now + 60_000` to inspect interval claims approaching recovery. Adjust the threshold to your polling interval and storage latency; do not treat it as a built-in alert limit. The fields below are internal storage details, not a new public API.

## Redis

Iterate the hash with `HSCAN josk:app:tasks 0 COUNT 100` until the cursor returns to zero (or `josk:{app}:tasks` with `useHashTags: true`). Parse each value as JSON and select `isInterval === true`, a non-empty `claimLeaseId`, and `executeAt <= Date.now() + 60_000`. Repeat `HSCAN` with the returned cursor; do not use `HGETALL` on a large hash. `ZCOUNT schedule -inf now` alone counts due work, not stuck work.

## MongoDB

```js
const threshold = new Date(Date.now() + 60_000);
db.getCollection('__JobTasks__app').find({
  isInterval: true,
  isDeleted: false,
  claimLeaseId: { $type: 'string', $ne: '' },
  executeAt: { $lte: threshold }
});
```

## PostgreSQL

```sql
SELECT uid, execute_at, claimed_at
FROM josk_tasks
WHERE prefix = 'app'
  AND is_interval = true
  AND is_deleted = false
  AND claim_lease_id IS NOT NULL
  AND claim_lease_id <> ''
  AND execute_at <= (EXTRACT(EPOCH FROM CURRENT_TIMESTAMP) * 1000)::BIGINT + 60000;
```

Task timestamps are generated by application nodes even with PostgreSQL storage. Keep node clocks synchronized before comparing them with server time.

## Recovery after a kill

Re-registering an already claimed interval preserves its existing zombie deadline. If its process dies without calling `ready()`, another instance may wait the full `zombieTime` (15 minutes by default), not merely the interval `delay`. This prevents a rolling deploy from scheduling a duplicate while the original handler is still active. Set `zombieTime` above the slowest legitimate handler runtime plus margin; values below 60 seconds are not recommended. Lowering it below a valid runtime trades faster recovery for overlapping executions.

Before this change, a completed task could leave `claimLeaseId` in storage. On the first registration after upgrading, it may retain that old date rather than reset to `now + delay`; the next successful `update()` clears the stale marker. During a mixed-version rollout, old instances can still shorten claims. `destroy()` stops polling but does not await handlers or release their claims; handle process shutdown accordingly. A lease-fenced `update()` for stale handlers and graceful claim release are future work.

The `onError` notice "One of your tasks is missing" means this instance has no handler registered for a task it claimed. It does not report an otherwise registered handler that exceeded `zombieTime`.
